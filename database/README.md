# Database

This project did not previously ship its schema in git. As we make
schema changes for security/feature work, the DDL lands here as
numbered SQL files (`0000_*.sql`, `0001_*.sql`, ...).

## Running migrations

Two ways to run them.

### Option 1 — one combined file (easiest for phpMyAdmin)

`database/migrations_combined_phpmyadmin.sql` is an
auto-generated bundle of all seven files **in the correct order**
with the `DELIMITER //` directives stripped (some phpMyAdmin
versions can't parse them). Import this single file via
phpMyAdmin → **Import** → **Choose File** → Go.

Re-generate the bundle whenever a new per-file migration is added:

```bash
scripts/build_combined_migration.sh
```

### Option 2 — per-file (mysql CLI or modern phpMyAdmin)

Each file is safe to run **once** against the live MySQL database
and (where MySQL allows) idempotent on re-run. Run them in order:

## Why each migration exists

| File | Why |
|---|---|
| `0000_schema_fixups.sql` | **Must run first.** Widens `admin.admin_password` to 255 chars (bcrypt is 60 chars; the existing `varchar(50)` would silently truncate it and lock the admin out on the next login). Adds `admin.banned` flag (referenced by `Adminmodel::login`). Widens `user.email_id` to 255 and adds a UNIQUE index. Adds a slug index on `listings`. |
| `0001_auth_flows.sql` | Password-reset (`password_resets` table) + email-verification columns on `user`. Back-fills `email_verified = 1` for existing rows so legacy accounts aren't locked out. |
| `0002_services.sql` | IT/web services catalog (`services`, `service_requests`). Seeds 10 placeholder services — edit in `/admin/services` to match the real Space Center Systems catalog. |
| `0003_newsletter_campaigns.sql` | `newsletter_campaigns` + `newsletter_campaign_sends` so the admin can compose, queue, and batch-send emails to the existing subscriber list. |
| `0004_rate_limits.sql` | `rate_limits` table backing the `Rate_limit` library. Protects login, register, password-reset, enquiry, review, newsletter signup, and service-request endpoints from brute-force / spam. |
| `0005_admin_roles.sql` | Adds `admin.role` (`super_admin`/`editor`) + `admin.is_active`. Promotes the seeded admin (id=1) to `super_admin`. Sub-admin management, billing, and ad-sales screens are gated to super-admins; editors can manage content. |
| `0006_ad_zones.sql` | Adds `ads_prices.slot_key` so the frontend ad-slot partial (`application/views/partials/ad_slot.php`) can request "the ad for the home-hero slot" by code rather than admin-typed name. Seeds 8 canonical slots: `home-hero`, `home-sidebar`, `listing-sidebar`, `listing-top`, `listing-inline`, `events-sidebar`, `news-sidebar`, `footer-banner`. |
| `0014_plan_category.sql` | Adds `plans.category` — the advertising-catalog group slug (`business-listing`, `add-ons`, `site-wide-banners`, `category-banners`, `site-wide-videos`, `category-videos`, `special`). Lets the admin and public pricing pages render packages under their catalog section headings. Populated by `seeds/pearland411_packages.sql`. |
| `0017_home_ad_slots.sql` | Seeds the homepage ad zones. Each `slot_key` is deliberately the **same string as the `plans.slug`** of the package sold on `/pricing-plan` (`top-banner-site-wide`, `bottom-banner-site-wide`, `middle-banner-category`, `right-side-banner-1/2/3`, `right-panel-skyscraper`), so a purchase maps to a position on the page — previously ad zones and sellable packages were two unrelated vocabularies. **Data only** (0006 added `slot_key`/`size`), so no DDL and no `DELIMITER`; standalone file and combined-bundle block are identical. |
| `0018_homepage_promos.sql` | Adds `listings.hotspot_until` and `listings.week_until` (both `DATE NULL`, indexed). These record the **Business Hotspot on Homepage** ($25/30d) and **Business Of the Week** ($20/7d) packages, which were already sellable but had nowhere to be stored, so the homepage could never render them. Dates rather than flags, so a placement expires on its own at the end of the paid term. |
| `0019_directory_ad_slots.sql` | Seeds the three **category-priced** ad zones the directory (`/all-listing`) and listing-details pages render: `right-banner-1`, `right-banner-2` and `bottom-banner-category`. Same rule as 0017 — each `slot_key` is the `plans.slug` of a package sold on `/pricing-plan`; those three were sellable but had no `ads_prices` row, so nothing bought for them could ever appear. Sizes are `300x250` for the right banners (they sit in a sidebar column, not the 900x100 the packages seed still claims) and `900x100` for the category bottom banner. **Data only**, so the standalone file and the combined-bundle block are identical. Note: the 0006 zones `listing-top` / `listing-inline` / `listing-sidebar` match no package and are no longer rendered directly — the two views pass them as `$slot_alias`, so an ad an operator booked against one by hand still runs in the equivalent new position. |
| `0020_listing_status_normalise.sql` | **Fixes the "255 listings" box over a page showing 13.** `listings.listing_status` is read as `1` = published everywhere (admin listings table, both user dashboards, sitemap, every public query), but almost nothing wrote `1`: the admin CSV import hardcoded `0`, and the public add-listing form wrote the *string* `'Active'` into an `INT` column, which MySQL coerces to `0`. So imported and user-submitted businesses were all stored unpublished — the category counters (which filtered only `is_deleted`) counted them, the listing queries (which also filtered `listing_status = 1`) didn't. Backs the old values up to `listings.listing_status_backup` first, then publishes every non-deleted listing that is `0` or `NULL`. Also backfills `listing_categories.category_slug` where it is empty, using the same rule as `pearland_slug()` in `application/helpers/view_helper.php`, so admin-created categories stop relying on a name-matching fallback the three menus each guessed differently. Idempotent: the backup column is the guard, so a re-run cannot re-publish something an operator has since switched off. **Rollback:** `UPDATE listings SET listing_status = listing_status_backup WHERE listing_status_backup IS NOT NULL;` |
| `0021_blog_dates.sql` | **Fixes "all blogs have the same date".** `Admin::add_blog()` never wrote `blogs.created_at` — the payload it builds has user_id, name, description, status, isenquiry and slug and nothing else — so admin-created posts took the column default (zero date / NULL). The index then printed `date('d, M Y', strtotime(...))`, and `strtotime()` returns `FALSE` for those, which `date()` renders as the epoch: every dateless post showed the *same* date. Makes the column nullable with `DEFAULT CURRENT_TIMESTAMP` so a write path that forgets still records something real, and turns existing zero dates into `NULL`. It deliberately does **not** invent dates — there is no signal in the row for what the real one was; `NULL` is honest and the views now omit the line. Set the true dates per post at `/admin/blog-list` → Edit, which grew a **Publish date** field alongside this migration. Idempotent. |
| `0022_listing_deleted_date.sql` | **Fixes "Deleted listings cannot be restored — HTTP 500".** `Admin::restore_listing()` read the trashed row, set two properties on it, and wrote the whole object back — including `deleted_date`, a column that appeared exactly **once** in the entire application, on that line. Nothing created it and nothing else wrote it: the soft delete set only `is_deleted = 1`, and the trash page's "Deleted Date" heading was being filled with `postal_code`. So the UPDATE emitted `SET … deleted_date = '…'` against a column that does not exist → MySQL 1054 → the 500. The column is added rather than removed from the code, because a trash page that cannot say when something was deleted is not much of a trash page: `softDeleteListing()` now sets it and `restoreListing()` clears it (the old code *stamped* it with "now" while restoring, which was backwards). Existing trashed rows get NULL — there is no signal in the row for when they were deleted, and the view prints `''` rather than inventing one. Idempotent. |
| `0023_listing_subcategory_map.sql` | **Fixes "why can't I add subcategories, even though I have included all the available subcategories?"** It was never possible. `listings.sub_category_id` is a single INT column and the admin form posted a single-value `<select>`, so a listing could hold exactly one subcategory and the last one picked won. `listing_sub_categories` is the **catalogue** of subcategories, not a listing-to-subcategory join, and no join table existed anywhere in the schema. Adds `listing_sub_category_map` (composite primary key, so a pair cannot be recorded twice) and back-fills the existing single values, so nothing already recorded is lost. `listings.sub_category_id` deliberately **stays**, holding the first selection: it is read by the admin listings table, the CSV export, the public listing page and several model joins, and retiring it belongs in its own migration. Idempotent. |
| `0024_ads_category_target.sql` | **Fixes "no option to add category-specific banners and header banner in Business Listings."** Ads had exactly one targeting dimension — `ads_prices.slot_key`, the position on the page — and the booking form offered user, price, dates, artwork and a link, with no category anywhere. The slot keys that read as category-specific are not: `middle-banner-category` is one global inventory item included by eight views, so "category" meant *rendered on category pages*, not *sold per category*. Adds `ads.category_id`, nullable: NULL runs the ad in its slot everywhere (every ad booked before this migration), an id restricts it to that listing category, and a category booking outranks an untargeted one in the same slot. Also seeds `top-banner-category`, the directory header slot the report asks for, following the 0017/0019 rule that a `slot_key` is the `plans.slug` of the package sold for it. Idempotent. |
| `0025_ad_zone_reconciliation.sql` | **Moves ads booked against positions that render nowhere onto positions that do, and takes the dead positions out of circulation.** A page asks for a zone by `ads_prices.slot_key`; the rows made by hand before 0006 have none — `Above Footer Left`, `Feature Business Right 1`, `Home Page Below Slider left` and the rest — and the six `Usermodel::get*Ads()` methods that once drew them are dead code no view calls. So an ad booked against one is paid for, dated, approved and appears on zero pages. Repoints those bookings onto the equivalent live zone, then sets the dead rows inactive (**not** deleted; each booking keeps its own `ad_cost_per_day` / `ad_total_cost`, so billing history is untouched). Also retires `footer-banner` — it has a slot_key but no view includes it any more and no package sells it — backfills any missing `size`, and seeds `ads_house_max_per_page`. **Run `database/ad_zone_audit.sql` first**: it is read-only and shows exactly what this will touch, including whether anyone has paid for a zone that renders nowhere. Check the name mapping in step 1 before running. Idempotent. |
| `0026_enquiry_departments.sql` | **Fixes "client message doesn't go to marketing package" and removes the departed staff names from the public forms.** Every public message landed in one pile: the callback panel on `/pricing-plan` and the `/contact-us` form both post to `/contact-submit`, and both were written with `enquiry_type = 'contact'`. The only thing separating them was the free-text `enquiry_source`, which nothing filtered on — so somebody leaving a phone number to *buy a package* arrived looking exactly like a general question and could sit unread among them. Package leads now file as `enquiry_type = 'package'` with their own tab at `/admin/enquiries`. Adds `enquiries.enquiry_department` plus an index on `enquiry_type`, reclassifies the callback requests already in the table and backfills their department, and deletes the `sales_representatives` setting — the nine named reps shown on the live site come from that row, not from code, and most of them no longer work here. The department list itself is deliberately **not** seeded: blank means "use the built-in list" in `enquiry_departments()`. `enquiries` predates this repo's migrations, so every step is guarded on the table existing. Idempotent. |
| `0027_category_header_banner.sql` | **Finishes "No option to add category-specific banners and header banner in Business Listings."** `0024` covered the *sold* half — `ads.category_id` lets an advertiser buy a banner that runs in one category only, and it seeded the `top-banner-category` zone. This adds the *editorial* half: `listing_categories.category_banner`, the category's own wide header artwork, uploaded at `/admin/edit_listing_category/<id>` and rendered as the hero of `/all_listing/<slug>`. Every category previously drew the same hard-coded photograph, so Restaurants and Plumbers looked identical at the top of the page. Separate from `category_image`, which is resized to 400x250 as a card thumbnail — a different shape for a different job. NULL means "use the standard directory header", so there is no seed and no backfill and every existing category is unchanged. `listing_categories` predates this repo's migrations, so the step is guarded on the table as well as the column. Idempotent. Depends on nothing. |
| `0028_admin_billing.sql` | **Backs `/admin/billing`, the screen that answers "where do I add a customer's card?"** — there was no answer. A card could only ever be vaulted by the *customer*, inside `User::process_checkout()`, and only if they ticked auto-renew during their own checkout: `activateHelcimSubscription()` is the sole writer of `payment_cards`, and it stores `card_last4 = '0000'` / `exp 1/2099` placeholders because nothing displayed them. Staff signing a business up over the phone had no path at all, so `Cli::renew_subscriptions` found no token and skipped the row. Adds five columns, all nullable or defaulted, so nothing existing changes and nothing is back-filled: `payment_cards.card_brand` and `payment_cards.card_source` (`customer` = self-serve checkout, `admin` = keyed in by staff) so the screen can say what the card is and where it came from; `payment_cards.added_by_admin_id` and `transactions.created_by_admin_id` as an audit trail for money a person moved by hand; and `transactions.note` ("August 2026 bill"), because a one-off staff charge was otherwise indistinguishable in the history from an automatic renewal. Deliberately adds **no** column that could hold a PAN, expiry or CVV beyond the last four digits — HelcimPay.js tokenizes card data in the browser and `pan_encrypted` stays NULL, as 0012 established. Idempotent, and every step guarded on its table existing as well as its column. |
| `0029_billing_per_business.sql` | **Bills a business, not an account, and lets staff agree a price.** 0028 keyed `/admin/billing` on `user`, because that is what `subscriptions` and `payment_cards` are keyed on — but the listings here were bulk-loaded under a handful of data-entry logins, so one account owns dozens of unrelated businesses. Searching "central bbq" returned the import account *10 dollars Galveston shuttle* with a hundred business names strung after it, and billing that row would have billed all of them at once. Adds `subscriptions.listing_id` (NULL = account-level, which is every existing row and everything the self-serve checkout creates), `subscriptions.custom_amount` (an agreed price that overrides the plan's on every renewal — a package sets the entitlements, this sets what is charged, so a founding-member rate no longer breaks the first time the plan's list price is edited), and `transactions.listing_id` so history reads per business. Also seeds `billing_notify_emails`. All nullable, nothing back-filled, both new indexes guarded. Idempotent. |
| `0030_subscription_term_columns.sql` | **Creates the `subscriptions` columns the code has always written but no migration ever added.** Found by `/admin/billing-customer/<id>` returning HTTP 500: it asked for `subscriptions.duration_id` and `duration_days`, and MySQL answers a missing column with error 1054 rather than a NULL. Those — plus `duration_months`, `total_amount`, `currency`, `billing_cycle`, `payment_status`, `start_date`, `last_transaction_id` — are written by `Usermodel::activateHelcimSubscription()`, the self-serve checkout, and appear in no `ALTER TABLE` in this repo. On a database where no customer ever completed a checkout they were never created, **which means the checkout has been broken here the whole time, in the same way and for the same reason**; nobody noticed because nobody had bought anything. Each column is added only when missing, so a database where a checkout did once succeed is untouched. The application no longer depends on this file (the billing screen reads the subscription with `SELECT *` and treats every one as optional; the writes drop unknown columns), but run it anyway — without `duration_days` a renewal cannot know its own term length and every subscription silently falls back to 30 days. Idempotent. |
| `0031_category_dedupe.sql` | **Fixes "/all-category lists the same category twice."** The index offered `Arts & Entertainment` (4 businesses) beside `Arts and Entertainment` (6), `Beauty & Personal Care` (26) beside `Beauty and Personal Care` (25), and `Community & Government` (empty) beside `Community and Government` (14) — two URLs, two counts and two directory pages for one kind of business, with the businesses split between them and neither page admitting the other existed. The directory was seeded more than once from sources that punctuated their taxonomy differently, and nothing in the application has ever compared two category names. Merges only what is the same name once normalised — lower-cased, `&` read as `and`, punctuation dropped, whitespace collapsed, matching `pearland_merge_key()` in `application/helpers/view_helper.php`. The survivor is the one with the most published listings (lowest id breaks the tie) and inherits the loser's slug only if it has none of its own, so no indexed URL is thrown away; `listings`, `listing_sub_categories` and `ads.category_id` are all re-pointed, and each merge is recorded in `listing_category_merges` before the duplicate row is deleted. It deliberately does **not** merge judgement calls like Finance / Financial Services or Education / Education & Childcare — those are one category or three depending on how the directory wants to read, and `/admin/all_listing_category` grew a Merge control for making that call. Idempotent. |
| `0032_listing_dedupe.sql` | **Fixes "the category says 42 businesses and the first page repeats the same shops."** Same cause as 0031 — the directory was seeded more than once — and the count was never wrong: there really are 42 rows, several of them the same business twice. Matches on the same name once case and punctuation are out **and** one hard identifier in common, in three passes: the phone number (digits only, last ten, so `+1 281-992-2064` and `(281) 992 2064` are one number), then the street address, then the website host. Name alone is never enough — Pearland has more than one Subway. **It will not touch a listing with an owner** (`user_id > 0`): claimed listings are somebody's property, quite possibly somebody's paid package, and where two claimed rows collide both are left exactly as they are for `/admin/duplicate_listings` to show a person. The loser is soft-deleted (`is_deleted = 1`, `deleted_date = NOW()`), so reviews and enquiries stay attached and it is one click from restoring at `/admin/trash_listings`; every action is recorded in `listing_duplicate_merges` first. **Run after 0031.** Idempotent. **Rollback:** `UPDATE listings l JOIN listing_duplicate_merges m ON m.listing_id = l.listing_id SET l.is_deleted = 0, l.deleted_date = NULL;` |
| `0031_email_log.sql` | **Records every email the site tries to send, so "the verification email never arrived" stops being unanswerable.** In September 2026 signup confirmations and password resets stopped being delivered on the live site — not to Spam, simply gone — and nothing in the application could say whether a message had been refused by the relay, accepted and then discarded by the recipient, or never attempted at all: the only failure report was a `log_message('error')` going to `application/logs/`, a directory that does not exist on a fresh deploy, so CI's logger disabled itself and the error was dropped. Creates `email_log` — recipient, subject, type, transport, sent/failed, and the truncated SMTP error — written by `Mailer::record()` and read by `/admin/email-diagnostics`. Sending works without this table (the mailer checks `table_exists` first and skips the write), you just cannot see what happened afterwards. New table only, nothing altered, nothing back-filled. Idempotent. Depends on nothing. |
| `0033_plan_catalog_corrections.sql` | **Corrects the advertising catalog on `/pricing-plan`** (tracker #26, #19). The seed is not re-run on live, so the fixes come as data: the right-hand banner packages described as "900x100" are rewritten as **300x250** (the size their zones actually render — only rows still carrying the seeded text are touched); the **"Skyscraper"** package (slug `skyscraper`) is taken off sale because no page renders a `skyscraper` zone, so it could be bought and never shown (not deleted, and skipped if such a zone has since been created); a sellable **Category Header Banner** plan is seeded for the `top-banner-category` zone 0024 created without a plan, with its 30-day base term; and `transactions.target_category_id` records which category a category-specific banner or video was bought for (checkout now asks). Prices are deliberately not changed — that is the client's call at `/admin/pricing-plan`. Idempotent. |
| `0034_review_dedupe.sql` | **One review per member per business** (tracker #18). `submit_review` never checked for an earlier review, so Back, refresh or a double click each added a copy that counted towards the average. Copies a member's older reviews of the same listing into `listing_reviews_dedupe_backup` (same columns — nothing is lost), deletes them keeping the newest, then adds `UNIQUE KEY listing_reviews_one_per_member (listing_id, user_id)` — only if no duplicate pair remains, so it cannot fail half-way on odd legacy rows. Refreshes `listings.average_rating` / `total_reviews` where those columns exist. Idempotent. |
| `0035_bylines_and_member_ban.sql` | **Bylines and member suspension** (tracker #20, B2). `news.news_byline` / `blogs.blog_byline` (NULL = print the owning account's name, as before) back the new Byline box on the admin news and blog forms. `user.banned` is written by Suspend / Restore at `/admin/users`, refused at login and checked on every request; it is part of the live schema already (login reads it) and is only added where missing. Idempotent. |
| `0036_tracker_round3.sql` | **Tracker round of 2026-10-19.** `plans.listing_video_limit` (default 1; the special package -1 = unlimited, set only when the column is created) caps the YouTube links on a listing, beside the existing `photo_limit` — editable at `/admin/pricing`. `ads.listing_id` records the business a category banner was booked for from its admin edit screen (`Admin::listing_banner_add`). `listings.cover_image` (the listing page's header banner) is added only where missing. `subscriptions.renewal_reminded_for` lets `Cli::renew_subscriptions` email the customer once before each auto-renewal charge. Back-fill: enquiries about a listing whose owner's claim was approved are re-addressed to that owner, so their earlier leads reach their dashboard. Idempotent. |
| `0015_plan_durations_columns.sql` | Creates `plan_durations` when missing and back-fills `currency` / `duration_days` / `is_active` / `created_at` / `updated_at` on databases that predate them. **Required** — without it `Adminmodel::updatePricingDuration()` writes a column that does not exist, so saving a duration price in admin silently does nothing. |
| `0016_transaction_term.sql` | Adds `term_days`, `expires_at` and `duration_id` to `transactions` so an ad placement bought for a longer term (12 months, 2 years) records its real expiry instead of being reported against the plan's 30-day base period. Back-fills existing rows from the plan's base term. |
| *(seed)* `seeds/homepage_ad_zones_only.sql` | phpMyAdmin-friendly version of 0017 for sites that **already have real listings**: adds only the five homepage ad zones and switches on the News / Videos / Events services. Inserts no listings, categories or content. Use `seeds/pearland_sample_content.sql` instead only on an empty/demo database. |
